### Decisions and findings

- `src/repos/ai-config.ts` (in-tree version kept): `asPlatformAdmin` sets transaction-local `app.is_platform_admin` before reading `platform_superadmins` (whose SELECT policy requires it), then checks the persisted non-revoked grant and the active local membership, and binds `app.platform_actor_workos_user_id` only after both pass. Before the checks pass, only those two fixed repository queries run; no caller SQL or callback can execute. A failed check throws inside `withTenantTransaction`, which issues `ROLLBACK`, so the `set_config(..., true)` value is discarded with the transaction. Compared with the earlier `withGlobalTransaction` design, the checks run in the same transaction as the writes (no cross-transaction gap), and no `FOR SHARE` is used on the checks. The write policies still re-check the grant through `app.is_platform_actor()`. No weakening was found, so the separate global transaction was not reintroduced.
- Helper scope: the WIP helper allowed only tenant admins, and the WIP pin trigger still locked directly, so ordinary-member pins could never work. No platform-admin code path activates or pins: activation is `asTenantAdmin`, pins run in ordinary tenant transactions, and platform repositories use `withGlobalTransaction` without touching activations or pins. The earlier platform-actor branch was therefore omitted. In its place, an active member may lock only the shared base of the tenant's current active release, which is exactly what the pin trigger needs. Assertions check that a tenant admin gets `true` but cannot UPDATE or directly `FOR SHARE` shared rows, that a member gets `true` for its active base and `false` for an unrelated release, that a forged cross-tenant context gets `false`, and that PUBLIC lacks EXECUTE.
- Migration `1792378759000` (member SELECT policy on `ai_shared_releases`) was not required and was removed. Its subquery was tenant-bounded by the existing RLS on activations and releases, so it did not expose other tenants' releases. But a SELECT policy cannot satisfy the UPDATE-policy requirement of `FOR SHARE`, and the helper covers the pin path. Members now have no new read path; the integration test asserts a member reads zero shared rows.
- Migration naming: the replacement uses a new name and timestamp (`1792378760000`, which sorts after every committed migration). Any database that had applied the uncommitted WIP files would therefore fail loudly on missing files instead of silently keeping the WIP trigger bodies. No such database was inspected.
- Product repair in `src/repos/ai-turns.ts`: `claimTurn` inserted with `ON CONFLICT (tenant_id, conversation_id, request_id) DO NOTHING`. A concurrent duplicate request could hit the one-open-turn partial index first and raise a unique violation, which made the upgrade run flaky. A different request while a turn was open always raised it, so the existing `in_progress` fallback was unreachable. The insert now uses `ON CONFLICT DO NOTHING` without a target. Regression coverage asserts the open-turn `in_progress` case and five repeated three-way races. Reverting the fix makes the suite fail with `ai_turns_one_open_per_conversation`.
- Fixture corrections that do not weaken assertions: turns follow `reserved → extracted → effects_committed → responded`; the third attempt names a configured profile and must fail with the Spanish fallback-sequence error; usage is asserted as deltas. Replay after trace scrub is asserted as `completed` with null input and response and the same turn ID; this matches the persistence contract, which keeps the request ID, hash, and stage. Changed input on that request ID still returns `conflict`. The unrelated task outbox artifact is asserted to survive the scrub.
- Not verified, likely a KAN-71 integration defect outside this repair (from reading the code only): `resolveNewConversationRelease` materializes a module assignment or global-default shared release. It locks the shared row with a direct `FOR SHARE`, which RLS filters for tenant users. It inserts `ai_releases` as the conversation user, which the tenant-admin `WITH CHECK` rejects for members. It then pins a release that is not the active activation, which the pin trigger rejects. No integration test covers this path.
