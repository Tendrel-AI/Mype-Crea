# CreaMype operations guide

This guide covers how to set up, run, test, and operate CreaMype as the repository stands on
`developer`. It names environment variables only; values live in `.env.local` (local) or the
hosting provider's secret store, never in git. Items marked **Pending** are open decisions or
unverified states. Do not treat them as done.

Related records: [`pipeline/kan-62-topology.md`](../pipeline/kan-62-topology.md) (deployment
topology, KAN-15), [`pipeline/kan-63-recovery-plan.md`](../pipeline/kan-63-recovery-plan.md)
(task recovery, KAN-18), [`pipeline/kan-61-ci-policy.md`](../pipeline/kan-61-ci-policy.md) (CI),
and [`pipeline/kan-69-audit-2026-10-21.md`](../pipeline/kan-69-audit-2026-10-21.md) (LLM
provider switch).

## 1. Phase 1 scope and limits

- One institutional pilot tenant. Tenant access comes from persisted organization records and
  WorkOS membership, not from environment variables.
- Only `logo-agent` produces deliverables. Other agents in the wizard are not live.
- The logo worker runs inside the Next.js process. There is no separate worker command, and
  multi-replica behavior has not been reviewed (see section 8).
- Two public probes exist: liveness `GET /api/health` and readiness `GET /api/health/ready`
  (section 9). They report status only, never dependency details.
- Logo images are generated by fal.ai. Private object storage and signed asset URLs are not
  integrated yet (KAN-52).
- Evals are a manual metrics report, not a CI gate, and run only with owner approval.

## 2. Prerequisites

- Node.js 20 or newer (CI uses Node 22) and npm.
- Docker with Compose, for the local PostgreSQL and Redis services.
- Accounts and keys for the services you will exercise (section 3). A local run without
  LLM or fal.ai keys can start, but chat and logo generation will fail.

## 3. Services

| Service | Used for | Required | Notes |
|---|---|---|---|

| Redis 7 | Wake-up channel (Pub/Sub) for the durable logo worker and orchestrator notifications | For end-to-end logo persistence | Without Redis the app uses in-process notifiers and `LocalAdapter`; logo deliverables are not persisted for display. | WorkOS AuthKit | Sign-in, organizations, MFA for platform admins | Yes | |
| OpenRouter or Anthropic | Text models (extractor, responder, eval judge) | At least one | See section 5. |
| fal.ai | Logo image generation | For logos | Independent of the LLM provider choice. |
| LangSmith | Eval experiments and development tracing | Optional | Tracing is ignored when `NODE_ENV=production`. |

## 4. Environment variables (names only)

The template with comments is [`.env.example`](../.env.example). Copy it to `.env.local`.

| Group | Variables |

| Redis | `REDIS_URL` |
| Auth | `WORKOS_API_KEY`, `WORKOS_CLIENT_ID`, `WORKOS_COOKIE_PASSWORD`, `NEXT_PUBLIC_WORKOS_REDIRECT_URI`, `PLATFORM_BOOTSTRAP_SUPERADMIN_WORKOS_USER_ID` (one-time bootstrap; clear after use) |
| LLM provider | `LLM_PROVIDER`, `OPENROUTER_API_KEY`, `ANTHROPIC_API_KEY`, `OPENROUTER_EXTRACTOR_MODEL`, `OPENROUTER_RESPONDER_MODEL`, `ANTHROPIC_EXTRACTOR_MODEL`, `ANTHROPIC_RESPONDER_MODEL` |
| AI release runtime (KAN-70) | `AI_CONFIG_RUNTIME_VERSION`, `AI_CONFIG_CODE_FINGERPRINT`, `AI_CONFIG_DEPENDENCY_FINGERPRINT`, `AI_CONFIG_OPENROUTER_ENABLED`, `AI_CONFIG_ANTHROPIC_ENABLED` |
| Images | `FAL_KEY` |
| Logging | `LOG_LEVEL` |

`APP_DATABASE_URL` to match.

## 5. LLM providers

Text-model calls go to one of two providers. Images always use fal.ai.

| Mode | Key | Extractor default | Responder default | Eval judge default |
|---|---|---|---|---|
| `LLM_PROVIDER=openrouter` (default) | `OPENROUTER_API_KEY` | `google/gemini-2.5-flash` | `google/gemini-2.5-pro` | `anthropic/claude-sonnet-5` |
| `LLM_PROVIDER=anthropic` | `ANTHROPIC_API_KEY` | `claude-haiku-5-5` | `claude-sonnet-5-5` | `claude-haiku-5-5` |

- Only the selected provider's key is required. An invalid `LLM_PROVIDER` value or a missing
  selected key fails with a clear error and never falls back silently.
- Model overrides are per provider. OpenRouter needs `provider/model` slugs; Anthropic needs
  direct `claude-*` IDs. Each client rejects an ID of the other shape before any network call.
- The extractor and the eval judge use forced tool calls. Claude Sonnet 5.5 rejects forced tool
  calls, so Anthropic extractor and judge overrides must be Haiku models.

### How the provider is chosen at runtime

- **Chat turns** run through the KAN-70 AI release runtime. Each conversation is pinned to a
  frozen AI release, and that release names the provider and model for each purpose, plus one
  cross-provider fallback profile. Chat turns do not read `LLM_PROVIDER`.
- `LLM_PROVIDER` and the model variables are read when a platform admin captures a baseline draft
  in **Configuración de IA** (`/admin/ai`): the selected provider becomes the primary profile.
  They also drive direct provider calls (evals and the eval judge).
- A fresh database has no AI release. Before the first conversation, a platform admin must
  capture a baseline draft, freeze it, and make it active for the tenant or as the platform
  default. New conversations fail until then. This sequence follows the code; it was not run end
  to end for this guide.

### Switching providers and rolling back to OpenRouter

- **Evals and direct calls:** set `LLM_PROVIDER` (and its key) and restart the process. To roll
  back, set `LLM_PROVIDER=openrouter` and restart.
- **Chat turns:** publish and activate a new AI release whose primary profiles use the target
  provider. Existing conversations keep their pinned release. To stop using a provider at once,
  set `AI_CONFIG_<PROVIDER>_ENABLED=false` (for example `AI_CONFIG_ANTHROPIC_ENABLED=false`) and
  restart, or disable it per tenant in `/admin/ai`; turns then use the release's fallback profile
  and record a notice.
- **Pending (owner decision):** KAN-69 asked for "one switch plus restart" and no automatic
  provider fallback. KAN-70 later introduced pinned releases with automatic compatible fallback.
  The two need to be reconciled; see the KAN-69 audit.

## 6. Local setup

1. `npm ci`
2. `cp .env.example .env.local`, then fill in the keys for the flows you need.
3. `npm run services:up` (PostgreSQL on `127.0.0.1:5434`, Redis on `127.0.0.1:6379`), then
   `npm run services:status` until both are healthy.
4. `npm run migrate:up` (uses `DATABASE_URL` from `.env.local`; confirm the target first).
5. `node --env-file=.env.local scripts/db-smoke.mjs` checks the runtime role and RLS posture.
6. Register the WorkOS organization for the pilot tenant through the platform flow. For a fresh
   install, set `PLATFORM_BOOTSTRAP_SUPERADMIN_WORKOS_USER_ID` before the first platform sign-in,
   then clear it.
7. Create and activate an AI release (section 5).
8. `npm run dev`, then open `http://localhost:3000`.

`npm run services:down` stops the containers and keeps their named volumes. Deleting a volume
destroys local data and is not a routine step.

## 7. Migrations, build, and start

- Local migrations: `npm run migrate:up`. `migrate:create`, `migrate:down`, and `migrate:redo`
  exist for development. They load `.env.local` and use `DATABASE_URL`. Do not run
  `migrate:down` against a database with data you need.
- Build: `npm run build` produces the standalone server in `.next/standalone`.
- Start: `npm start` runs that server with `HOSTNAME=0.0.0.0`, so it listens on all interfaces
  (see section 9). Set the same runtime variables as in development. With `REDIS_URL` set, the
  logo worker and the pending-task recovery scan start in this process.

### Automatic migrations on deploy (KAN-83)

Decided (owner, 2026-10-25): migrations apply themselves on every deploy, in development and
production. The Railway service's pre-deploy command is
`npm run migrate:deploy` ([`scripts/migrate-deploy.mjs`](../scripts/migrate-deploy.mjs)). Railway
runs it after the build and before the new version starts, in its own container started from the
built image, with the service variables and the private network (no volumes).

- **Connection.** It reads only `MIGRATION_DATABASE_URL`: the admin (migration owner) role of
  that environment's PostgreSQL, as a direct connection (not through PgBouncer in transaction
  mode, which breaks the session advisory lock). It never falls back to `DATABASE_URL`,
  `APP_DATABASE_URL`, or `.env` files, and app code never reads it. It refuses to run, with a
  one-line error and a non-zero exit, when the variable is missing or unparsable, names no user,
  uses `app_user`, or points at the same user, host, port, and database as `APP_DATABASE_URL`.
- **Run.** It applies pending migrations with node-pg-migrate `up`, using the same `pgmigrations`
  table, `public` schema, order check, and advisory lock as `npm run migrate:up`. All pending
  migrations run in one transaction. If another deploy holds the lock, it waits and retries
  (12 times, 5 seconds apart) and then finds nothing pending. With nothing pending it exits 0
  right after one connection and one query of the migrations table.
- **Logs.** The database name, the migration names, any failing SQL statement with its
  PostgreSQL error, and the duration. Never the URL, the password, or the host.
- **On failure** (bad variable, unreachable database, failing migration, lock still held after
  the retries) it exits non-zero, Railway does not retry it and aborts the deploy, and the
  previous version keeps serving. The single transaction rolls the batch back, unless a
  migration opts out with `pgm.noTransaction()`. Read the deploy logs, fix forward in a new
  commit, and deploy again.
- **A rollback does not undo a migration.** Redeploying an older version keeps the newer schema.
  That is safe only because migrations are add-only (below). Never run `migrate:down` against a
  deployed database to "match" a rollback.
- **No backup is taken by this step.** Recovery from a bad migration relies on Railway's
  scheduled PostgreSQL backups, which must be enabled in both environments (owner action, see
  section 9).
- **Timeout.** Railway gives the pre-deploy command no time limit by default. Set a Pre-deploy
  Timeout on the service so a migration stuck on a table lock fails the deploy instead of
  holding it open.

#### Add-only rule

The previous version keeps serving while the new one migrates and starts, so every migration
must work with the code already running. A migration's `up` may add tables, columns, functions,
policies, triggers, indexes, and grants. Destructive or renaming changes (`DROP TABLE`, `DROP
COLUMN`, `DROP FUNCTION`/`POLICY`/`TRIGGER`/`TYPE`, `RENAME`, `ALTER COLUMN ... TYPE`, `SET NOT
NULL` on an existing column, `TRUNCATE`) go in a **later** deploy, once no running version needs
the old shape. That file must say so with a marker comment that gives the reason:

```js
// destructive-ok: column note unused since the KAN-99 deploy
```

`scripts/__tests__/migrations-add-only.test.ts` (in CI's unit set) scans the `up` body of every
migration newer than `1792800002400_approval-owner-only` and fails on those statements unless the
file carries the marker. `down` is exempt. The scan is plain text, so it can flag a safe pattern
such as `DROP TRIGGER IF EXISTS` before re-creating a trigger; add the marker with the reason.

## 8. Tests and evals

| Kind | Command | Cost and risk |
|---|---|---|
| Unit tests | `npx vitest run <path>` for a focused check; `npx vitest run --exclude '**/*.integration.test.ts' --exclude 'evals/**'` for the CI unit set | Free. Fakes only, no network. |
| Typecheck and lint | `npx tsc --noEmit`, `npm run lint` | Free. |
| Integration tests | One `*.integration.test.ts` file at a time, against a disposable database | Writes to the database named in the environment. `npm run test:integration` loads `.env.local` and runs every integration file; use it only on an approved test database. |
| Evals | `npm run eval`, `npm run eval:extractor`, `npm run eval:responder` | **Real model calls that cost tokens.** |

**No real eval runs without explicit owner approval, for each run.** This applies even when keys
are present in `.env.local`. Start with one case (`npm run eval:extractor -- -t "<case id>"`).

To lower eval cost, the owner can approve a run with `EVAL_MODEL_PROFILE`:

| Value | OpenRouter extractor, responder, judge | Anthropic extractor, responder, judge |
|---|---|---|
| unset or `default` | normal defaults and overrides | normal defaults and overrides |
| `cheap` | `google/gemini-2.5-flash-lite` | `claude-haiku-5-5` |
| `free` | `google/gemma-4-31b-it:free` (rate-limited) | `claude-haiku-5-5` (no free tier) |

The profile only affects the eval process. It replaces the selected provider's model variables
and `EVAL_JUDGE_MODEL`, prints the models it applied, and records `modelProfile` in the
experiment metadata. Scores from a cheap or free run are not comparable with default-model runs.

CI (GitHub Actions, pull requests into and pushes to `developer`) runs lint, TypeScript, the
unit set above, a production build, migrations on an isolated PostgreSQL service, the
`app_user`/RLS check, and the two-tenant isolation suite. It uses no paid provider keys and
never runs evals. Tests under `evals/` are excluded from CI and run locally.

## 9. Deployment

Decided (KAN-15 / KAN-62): the pilot runs on the Railway project `Tendrel_AI / mype-crea`, with
`development` and `production` environments. The proposed topology is one persistent Next.js
instance per environment with its embedded logo worker, the existing Railway PostgreSQL and asset
bucket, and Redis per environment. `APP_DATABASE_URL` must use `app_user`; the admin role is
used only by the pre-deploy migration step through `MIGRATION_DATABASE_URL`. Reviewed source
moves from `developer` to `main` before production.

Service settings (set on each environment's app service, not in this repository):

| Setting | Value |
|---|---|
| Build command | `npm run build` |
| Start command | `HOSTNAME=0.0.0.0 node .next/standalone/server.js` (same as `npm start`; node runs directly so it receives `SIGTERM`) |
| Pre-deploy command | `npm run migrate:deploy` (section 7) |
| Healthcheck path | `/api/health/ready` |

The repository deliberately has no `railway.json`. Railway deprecated config as code
(`railway.json` / `railway.toml`): new services cannot opt in, and existing ones stop being read
on 2026-12-01. Its replacement, infrastructure as code (`.railway/railway.ts`: `build`, `start`,
`preDeploy`, `healthcheck`), cannot manage a service that also uses `railway.json`. Until the
owner adopts `.railway/railway.ts`, these settings are set in the service dashboard.

**Bind address.** The standalone server listens on `$HOSTNAME`. Railway sets `HOSTNAME` to the
container id, so without the override the server listened only on that name and Railway's
healthcheck could not connect: development deploy `9725ac7b` (commit `d0f5cd4`) failed
`/api/health/ready` with "service unavailable" for 5 minutes while the route never logged a
request. `npm start` sets `HOSTNAME=0.0.0.0`; with no start command on the service, Railpack
runs `npm start`. If a start command is set on the service, it must include the same prefix.
`scripts/__tests__/deploy-config.test.ts` checks the `start` script.

Deploy sequence (every deploy, automatic):

1. Railway builds the image.
2. The pre-deploy command applies pending migrations with `MIGRATION_DATABASE_URL`. On error the
   deploy stops here and the previous version keeps serving (section 7).
3. The new version starts with the runtime variables from section 4.
4. Railway waits for `GET /api/health/ready` to return 200 before switching traffic (see below).
   Then verify sign-in, a chat turn, and a logo end to end. The probes do not exercise WorkOS,
   the LLM provider, or fal.ai.

The deploy step does not take a database backup. Railway scheduled PostgreSQL backups (the
**Backups** tab of each PostgreSQL service) must be enabled in development and production; this
is an owner action and is not verified from the repository.

### Health and readiness probes

Both routes are public: `proxy.ts` excludes exactly these two paths from the WorkOS AuthKit
middleware, so they answer without a session and without WorkOS configuration. Any other path,
including other paths under `/api/health`, stays protected. Responses carry
`Cache-Control: no-store` and are never statically cached.

| Route | Checks | 200 | 503 |
|---|---|---|---|
| `GET /api/health` (liveness) | Nothing: the process is up and serving | `{"status":"ok"}` | Never |
| `GET /api/health/ready` (readiness) | PostgreSQL as `app_user` (`SELECT 1`); Redis `PING` only when `REDIS_URL` is set | `{"status":"ok","checks":{"database":"ok","redis":"ok"}}` (`redis` is `"skipped"` without `REDIS_URL`) | `{"status":"fail","checks":{...}}` with `"fail"` on each failing dependency |

- Each dependency has a 2-second budget and both run in parallel, so the probe answers in about
  2 seconds even when a dependency hangs. The database check runs in a read-only transaction
  with a local `statement_timeout` and binds no tenant, user, or admin context.
- The body never contains error messages, hostnames, connection strings, or environment values.
  The cause is logged server-side as `health.ready.dependency_failed` (scope `services.health`).
- Readiness does not prove sign-in, LLM, image generation, or the logo worker. It also does not
  check that migrations are applied; `SELECT 1` succeeds on an empty database. Migrations are
  guaranteed by the pre-deploy step instead (section 7): a deploy whose migrations fail never
  starts.

**Railway healthcheck path: `/api/health/ready`.** Railway calls the healthcheck path only while
a new deployment starts, and switches traffic once it returns 200. Gating on readiness keeps a
deployment that cannot reach PostgreSQL as `app_user` (for example, an empty or wrong
`APP_DATABASE_URL`, as seen on `mype-dev`) or a configured Redis from replacing a working one.
The probe runs only during deploys, so the load is negligible. Use `/api/health` for external
uptime monitors or a restart policy that must not depend on the database. If PostgreSQL is down
during a deploy, the new deployment fails its healthcheck and the previous one keeps serving.
The healthcheck path is a service setting, so it applies to every deployment of the service.
The server must listen on all interfaces for the probe to connect
(see **Bind address** above).

## 10. Recovery

Decided (KAN-18 / KAN-63, reversible local defaults):

- PostgreSQL `agent_tasks` is the source of truth; Redis only wakes the worker.
- With Redis, the process republishes due `pending` logo tasks right after the worker subscribes
  and every 60 seconds, at most 100 tasks per active tenant per pass. Claims are atomic, so
  duplicate wake-ups are safe.
- `in_progress` tasks are never replayed automatically, because the image provider may already
  have accepted the request. They stay visible for an operator.
- After an environment change, restart the app so service clients are recreated.
- A source rollback does not undo migrations (they apply automatically on deploy and are
  add-only; section 7). Prefer a reviewed forward fix; restore from backup
  only under the owner-approved procedure.
- Local services: `npm run services:down` then `npm run services:up` keeps the data volumes.

**Pending:**

- Production scan interval, batch size, alerting, and process ownership.
- When an `in_progress` task counts as stale, and who may retry it or mark it terminal.
- Maximum attempts and backoff for image-provider failures.
- Backup and restore targets, RPO and RTO, and a restore exercise (KAN-53).
